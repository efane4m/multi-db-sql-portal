# Результаты проверки backend — 23 октября 2026

Проверка выполнена на Windows, Python 3.12.14, Django 6.1.2, PostgreSQL 18.4.
Использован отдельный экземпляр PostgreSQL на loopback и отдельные `test_*` и
`validation_*` базы. Существующие пользовательские БД не использовались.
Docker CLI и настоящий Redis на этой машине недоступны; Docker-сборка здесь не
запускалась. Docker-конфигурация сохранена для воспроизводимой проверки команды.

## Что проверено запуском

- Django `check`; `makemigrations --check --dry-run`.
- JWT-вход, анонимный доступ, role=user/admin, отзыв доступа, новая регистрация БД.
- Реальное выполнение SELECT, JOIN, CTE и преобразование Decimal/date/bytea/NaN.
- Предпросмотр, сортировка, offset/limit, PK/FK, подсказки значений и их параметризация.
- Запрет DML/DDL/нескольких statements, INTO, блокировок, модифицирующих CTE,
  системных таблиц, неразрешённых функций/типов и конструкций SQL.
- Роль читает SELECT и не может DELETE даже после SET TRANSACTION READ WRITE.
- Настоящий PostgreSQL timeout и успешный следующий запрос после отмены.
- Серверные лимиты строк и байтов; повторяющиеся названия колонок требуют AS.
- Кеш пустого результата, refresh, нормализация комментариев, изоляция пользователей.
- Отказ Redis смоделирован через ошибки cache.get/cache.set: SQL продолжает работать.
- Журнал не содержит текстовых значений запроса.
- Закрытый файл пароля reader создаётся и читается следующими management-командами.
- Frontend: 190 тестов проходят; production-сборка Vite проходит.
- PowerShell-сценарий `scripts/check-backend.ps1` выполнен на живом Django HTTP
  сервере с настоящим JWT и validation_* данными; проверки успешно завершились.

Backend-набор: 28 успешно выполненных тестов; дополнительный opt-in тест
реального Redis пропущен. Для него нужна `PORTAL_TEST_REDIS_URL` — инструкция
в BACKEND.md. Кеш в функциональных и нагрузочных проверках — LocMemCache.

## Миллион записей и параллельные запросы

Генератор создал `bench_sale` с 1 000 000 строк, `bench_store` с 1 000 строк
и `bench_product` с 10 000 строк. На FK/дате/регионе созданы индексы, выполнен ANALYZE.
Три пробы каждого SQL, до двух запросов одновременно, API через Django/DRF client.
В таблице полное время API с созданием соединений/сериализацией; без сети/браузера.

| Запрос | Медиана без кеша, мс | Максимум, мс | Запрос с кешем, мс |
|---|---:|---:|---:|
| COUNT по миллиону строк | 197.03 | 298.90 | 137.02 |
| Индексный фильтр, 1 000 результатов | 89.92 | 112.06 | 29.84 |
| JOIN трёх таблиц + агрегирование | 444.95 | 569.01 | 27.54 |
| Большой результат, ограничен до 10 000 | 148.10 | 176.31 | 32.49 |

Схема — 24.24 мс; предпросмотр с точным COUNT — 134.51 мс; подсказки — 2.95 мс.
Все четыре запроса уложились в 5 000 мс на этом тестовом окружении.
Подсказки измерены на bench_store (1 000 строк), не на миллионе уникальных значений.

Первый прогон выявил JOIN >5 секунд. EXPLAIN обычного SELECT и серверного курсора
показали разные планы: курсор предпочёл Nested Loop/индексные проходы. Настройка
`cursor_tuple_fraction=1.0` в read-only транзакции позволила выбрать план с лучшей
полной стоимостью и уложиться в приведённое время. Оба плана сохранены в JSON.

Результаты: [backend-benchmark.json](backend-benchmark.json).

## Память

Дополнительный последовательный прогон с tracemalloc: пик Python allocations
10 007 451 байт (около 9.54 MiB) на весь бенчмарк. Это не RSS процесса и не память
PostgreSQL/libpq. Включение tracemalloc увеличивает время, поэтому его значения
не смешиваются с основной таблицей. Сервер возвращает максимум 10 000 строк;
браузерная виртуализация 100 000 строк этим прогоном не проверяется.

Результаты: [backend-memory-benchmark.json](backend-memory-benchmark.json).

production-сборка и полный backend-набор: 28 успешно, 1 opt-in Redis-тест пропущен.

тестовых данных.
