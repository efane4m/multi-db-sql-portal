# Конструктор выборок: дизайн фронтенда

Дата: 2026-10-22. Статус: на согласовании.

## Зачем это делается

Заказчику нужно показать модуль «Расширенный конструктор выборок ИСО» из технического задания. Пользователь собирает выборку из БД перетаскиванием полей в визуальное дерево условий вместо ручного написания SQL.

Главное на показе: **рабочая основа и приятный, удобный дизайн**. Заказчик смотрит, насколько легко собрать запрос и получить результат.

## Цели

- Новая страница конструктора в существующем React-приложении (`client`).
- Условия собираются перетаскиванием в дерево с группами И, ИЛИ, НЕ и вложенностью (не меньше 5 уровней).
- По дереву строится SQL, он показывается пользователю для проверки.
- Запрос выполняется через существующий бэкенд, результат показывается таблицей.
- Дизайн светлый и спокойный, понятный без обучения.

## Не цели

- Бэкенд не меняем: ни новых эндпоинтов, ни моделей, ни миграций.
- Нет JOIN между таблицами: запрос строится по одной таблице.
- Нет экспорта в XML, DBF, TXT, Word, Excel.
- Нет виртуализации таблицы и асинхронного выполнения с прогрессом.
- Нет истории запросов и настроек пользователя.
- Нет REST API для внешнего доступа к выборкам.
- Нет задания со звёздочкой (гистограммы, карта, PDF).
- Не переделываем существующие страницы (вход, профиль, ручной SQL).

## Анти-цели (провал, даже если формально работает)

- Конструктор работает, но выглядит как черновик или непонятен без объяснений.
- Пользователь может собрать условие, которое ломает запрос или меняет данные.

## Что уже есть и на чём строим

Проект: React 19 + Vite, `react-router-dom`, `axios`. Бэкенд: Django REST Framework с JWT.

Существующие API (адрес `http://localhost:8000`, заголовок `Authorization: Bearer <токен из localStorage>`):

- `GET /api/databases/` возвращает `{databases: [...]}` с базами, доступными пользователю (выдаются админом в админке).
- `POST /api/query/` принимает `{db_name, query}`, возвращает `{data: [ {колонка: значение} ], cached}` или `{error}`. Пропускает только запросы, начинающиеся с `SELECT`. Результаты кэшируются на 5 минут.

Страницы: `/login`, `/profile`, `/dashboard` (ручной SQL). Защита маршрутов через `PrivateRoute` в `App.jsx`.

## Что решено вместе с заказчиком проекта

- Макет: **три шага** на одной странице: 1) Условия, 2) SQL, 3) Результат. Шаг «Условия»: слева панель полей, в центре дерево условий.
- Стиль: **светлый, спокойный**: белые карточки на светло-сером фоне, мягкие тени, синий акцент. Группа И синяя, группа ИЛИ оранжевая (см. макет `.superpowers/brainstorm/*/content/visual-style.html`, вариант A). Условия соединены вертикальными линиями дерева.
- Пользователь выбирает базу из списка, который выдан ему администратором. Параметры подключения вводить не нужно.
- Состав работ:
  - Обязательно: выбор базы и таблицы, поля слева, дерево условий перетаскиванием (И, ИЛИ, НЕ, вложенность), операторы по типу поля, генератор SQL, выполнение, таблица результата.
  - Если хватит времени: undo/redo, подсказки значений при вводе, шаблоны с параметрами (`$Регион`), экспорт в CSV и JSON.

## Решения, принятые мной (проверьте)

Это мой выбор, а не договорённость.

1. **Схема таблиц** берётся запросом через `/api/query/`:
   `SELECT table_name, column_name, data_type FROM information_schema.columns WHERE table_schema = 'public' ORDER BY table_name, ordinal_position`.
   Таблицы `django_*` и `auth_*` скрываем.
2. **Тип поля** определяется по `data_type`: числовые (`integer`, `bigint`, `numeric`, `double precision` и т. п.), текстовые (`character varying`, `text`), даты (`date`, `timestamp*`), логические (`boolean`). Остальные считаем текстовыми.
3. **Операторы по типу:** числа и даты: `=`, `!=`, `>`, `<`, `>=`, `<=`, `BETWEEN`, `IS NULL`, `IS NOT NULL`. Текст: `LIKE`, `=`, `!=`, `IS NULL`, `IS NOT NULL`. Логические: `=`.
4. **Запрос по одной таблице**, выбираются все её поля. К запросу добавляется `LIMIT` (по умолчанию 1000, пользователь может поменять). Результат показывается с постраничным выводом на стороне клиента.
5. **Защита от SQL-инъекций на фронте:** значения всегда экранируются (одинарная кавычка удваивается, числа и даты проверяются по формату), имена таблиц и полей берутся только из списка схемы и заключаются в двойные кавычки. Причина: бэкенд проверяет лишь, что запрос начинается с `SELECT`, и других защит нет. Это ограничение бэкенда нужно озвучить заказчику отдельно.
6. **Перетаскивание:** выбор библиотеки за исполнителем (рекомендую `@dnd-kit`, она даёт аккуратные анимации и работает с вложенными зонами). Допустимо и нативное HTML5 drag-and-drop, если получится не хуже.
7. **Страница** `/constructor`, ссылка на неё с профиля. Остальные страницы не трогаем, общую светлую тему применяем только к новой странице.
8. **Хранение (если делаем шаблоны):** `localStorage` отдельно для каждого пользователя, ключ включает логин. Структура записи по смыслу таблицы `query_templates` из ТЗ: имя, описание, дерево условий, база, таблица, дата.
9. **Параметризованные шаблоны:** значение условия вида `$Регион` считается параметром. При запуске показывается окно, где вводятся значения параметров.
10. **Юнит-тесты** на генератор SQL (чистая функция: дерево на входе, строка на выходе): `vitest`. Остальные тесты не требуются.
11. **Язык интерфейса** русский.

12. **Проверено на проекте:** все три базы PostgreSQL, схема `public`. Запрос к `information_schema` из п. 1 возвращает таблицы и типы (проверено на `db_stores`: `stores_price`, `stores_product`, `stores_stock`, `stores_store`). Бэкенд выполняет запрос от имени сервисного пользователя БД, роль пользователя сайта на чтение схемы не влияет; на доступ к самой базе влияет (проверка `DatabaseAccess`).
13. **Кэш бэкенда:** ключ состоит из имени базы и текста запроса (не по пользователю), хранится 5 минут. Показываем отметку «из кэша» (поле `cached`). Кнопка «Обновить» выполняет запрос заново с добавлением в конец SQL комментария `/* refresh:<время> */`, он меняет ключ кэша.
14. **`LIKE`:** пользователь сам вводит `%` и `_`, мы их не экранируем. Кавычки внутри значения экранируются всегда.
15. **Параметры `$имя`** подставляются в значение до экранирования, затем весь результат экранируется как обычное значение.
16. **Даты:** в интерфейсе поле выбора даты, в SQL уходит ISO `YYYY-MM-DD`. Операторы для дат те же, что для чисел (п. 3), включая `=` и `!=`.
17. **Точка с запятой и комментарии** в значениях не запрещаем отдельно: значение всегда внутри строкового литерала с удвоенными кавычками, поэтому оно не может выйти из литерала. Числа проверяются по регулярному выражению и в кавычки не берутся.
18. **НЕ** это переключатель на любой группе: у группы есть признак «НЕ», он превращает её в `NOT (...)`. Корень дерева всегда группа (по умолчанию И). Пустое дерево даёт запрос без `WHERE`.
19. **Глубина:** жёсткого максимума нет. Интерфейс должен выглядеть аккуратно минимум на 5 уровнях вложенности (отступы, ширина карточек).
20. **Undo/redo:** состояние дерева с самого начала хранится как неизменяемый снимок с историей, чтобы отмену можно было добавить без переделки. Сама кнопка отмены входит в пункт «если хватит времени».
21. **Стили:** в `index.css` лежат стандартные стили шаблона Vite (в том числе `color-scheme: light dark`). Новая страница использует свой CSS-файл в своей папке и явно задаёт светлую схему, чтобы не зависеть от темы системы. Общие файлы не меняем. Макет-эталон по цветам и отступам: [query-constructor-style-mockup.html](query-constructor-style-mockup.html) (вариант A).
22. **Запросы к API и токен:** общего экземпляра axios нет, каждая страница сама ставит заголовок `Bearer`. Делаем маленький модуль в папке конструктора. При ответе 401 удаляем токен и переходим на `/login`.
23. **Таблица результата:** страница по 50 строк, клиентская сортировка по клику на заголовок колонки. Значения выводятся как строки, `null` показывается как «—».
24. **Бюджет:** срок не задан. Порядок работ: сначала основа (обязательный список), потом пункты «если хватит времени» по убыванию пользы для показа: undo/redo, шаблоны с параметрами, подсказки значений, экспорт CSV и JSON.

## Что остаётся на усмотрение исполнителя

Структура компонентов и файлов, формат внутреннего представления дерева условий, точные цвета и размеры, анимации, тексты подсказок и пустых состояний, обработка ошибок и состояний загрузки, доступность с клавиатуры.

## Критерии готовности

- Можно собрать вложенное условие глубиной не меньше 5 уровней и увидеть корректный SQL.
- Собранный запрос выполняется, результат виден в таблице; ошибки базы показываются понятным сообщением.
- Значение с кавычкой (`O'Brien`) не ломает запрос.
- Интерфейс остаётся отзывчивым при результате в несколько тысяч строк (постраничный вывод).
- Тесты генератора SQL проходят.
